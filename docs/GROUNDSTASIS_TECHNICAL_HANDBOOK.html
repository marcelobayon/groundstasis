A. System overview

The customer problem. A construction lender funds a building project in draws. Between draw inspections (often weeks apart) the lender has no independent way to know whether the site is actually progressing. A stalled project is a leading risk indicator, but it usually surfaces late — at the next inspection or when a draw request looks wrong. Ground Stasis watches a financed site by satellite and flags when it has gone unusually quiet, so a stall becomes an email this week rather than a surprise at the next draw.

What it is (and is not). It is an independent remote monitoring signal. It is not a replacement for physical inspection, fund control, appraisal, or underwriting judgment, and it never concludes that construction has "stopped" — only that observable surface change is unusually low. A cloudy or missing image is reported as a DATA GAP, never as inactivity. This integrity rule is enforced in code (see §C) and must be preserved in any change.

Two products on one engine. - One-time check ($9): a single live satellite read on one site → a status/score/confidence + an evidence timeline, emailed as a secure link. Proves the problem once. Model: SiteCheck. - Recurring monitoring ($19/$49/$99/mo): continuous monitoring of 1/3/10 sites with email alerts on stasis and resumed activity. Model: Site + Subscription. - Construction Draw Intelligence (CDI, +$15/site/mo): compares a customer-reported construction milestone against the satellite evidence and emails a finding when they diverge. Verified — src/lib/cdi/, SiteMilestone model, per-site drawIntelligence flag.

Positioning. Ground Stasis is framed as construction-activity-intelligence infrastructure — satellite imagery is one (swappable) sensor. The value stack is OBSERVATION → INTERPRETATION → STATUS → ALERT → WORKFLOW → API → DATA, and each layer is independently monetizable. See the project doc positioning.md.

C. Satellite data & analysis pipeline

This is the heart of the product and the most stable code. Two root docs are authoritative and should be read in full: SATELLITE_DATA.md (data source, CDSE Statistical API, evalscript, provider abstraction) and ALGORITHM.md (the full stasis heuristic, thresholds, and overrides). This section summarizes and points into the code.

Source. Copernicus Sentinel-2 L2A surface reflectance, via the Sentinel Hub Statistical API on the Copernicus Data Space Ecosystem (CDSE). The API computes cloud-masked, polygon-level statistics (NDVI, NDBI, BSI) server-side — Ground Stasis never downloads rasters. Verified src/lib/satellite/sentinelhub-provider.ts.

Provider abstraction. src/lib/satellite/provider.ts defines SatelliteProvider. Two implementations: DemoProvider (synthetic DEMO_SITE, the default when unconfigured) and SentinelHubProvider (CDSE). getSatelliteProvider() chooses by SATELLITE_PROVIDER and falls back to demo if the live provider is selected but unconfigured — the app never crashes for a missing key. Verified

Pipeline (one site):

getAvailableObservations (provider) → usability filter → site-level change → baseline
   → stasis score (0–100) → confidence (HIGH/MED/LOW, independent) → status → alert decision

Implemented in src/lib/analysis/* (pure) and orchestrated by src/lib/jobs/analyze-site.ts.

Integrity rules enforced in code (do not weaken): - A provider failure or insufficient/stale data → DATA GAP, never STASIS. Verified analyze-site.ts. - A STASIS score on LOW confidence is capped to REVIEW. Verified status.ts. - There is no automated ABANDONED/FRAUD status. The engine makes no legal/underwriting conclusion.

Versioning. Every evaluation records analysisVersion (stasis-v0.1) and thresholdsVersion (thresholds-v0.1). Historical scores are never silently rewritten; recalculation under a new version is explicit. Verified src/lib/analysis/config.ts.

Runtime-verify The CDSE response field names (outputs/bands/stats/percentiles) should be validated against a real API response the first time live credentials run; the parser is written defensively for this reason (noted in SATELLITE_DATA.md).

Limitations (state them to any customer). Satellite-derived surface change is indirect evidence of activity, not proof of completed work, contractor performance, loan compliance, or draw eligibility. Revisit cadence + clouds mean a usable image isn't guaranteed on any pass.

D. Application architecture & request lifecycle

Rendering. Next.js App Router. Public pages are server components, mostly static (prerendered at build). The account area and all /api/** handlers are dynamic (force-dynamic, server-rendered on demand). Heavy work never happens in a page render — it runs in the scheduled jobs.

The layered rule (still holds). src/lib/analysis imports nothing outside itself — pure, deterministic, fully unit-tested. Everything else (providers, db, jobs, api) depends inward on it, not the reverse. This is what lets the engine be tested in isolation and reused.

Key request flows (traced through real files):

  • $9 check: /construction-activity-check → components/check/CheckFlow.tsx → POST /api/checkout (Stripe Checkout, mode payment) → Stripe → POST /api/stripe/webhook (on checkout.session.completed) marks the SiteCheck paid → the single analysis runs via analyzeSite → result stored on the SiteCheck → emailed as a tokenized link → viewed at /check/[token].
  • Subscription: /#pricing (components/pricing-section.tsx) → POST /api/checkout (mode subscription) → Stripe → webhook recordStripeSubscription grants seats → sites created via repository.createSite (entitlement-checked) → monitored by the scheduled job.
  • Scheduled monitoring: scheduled-analysis (every 6h) → POST /api/analyze (admin-gated) → runScheduledAnalysis iterates getSitesDueForAnalysis → analyzeSite → persistAnalysis → alerts emailed + (new) webhook deliveries enqueued.

Error propagation. Providers throw → the job converts failures to DATA GAP (never stasis). API routes return a stable JSON error envelope (src/lib/api/errors.ts). Webhook delivery failures are retried from a durable outbox (§H). Metering/webhook emission are best-effort and never break the request that triggered them.

F. Authentication, authorization & account ownership

There are two credential systems; keep them straight.

1. Magic-link tokens (humans). src/lib/auth/magic-link.ts — HMAC-SHA256 signed, short-lived (MAGIC_LINK_TTL_MINUTES, default 30), rotatable (MAGIC_LINK_SECRET + …_PREVIOUS). Payload carries sub (subject) + scope. Scopes in use: account (the whole account), and per-site scopes (site:read / site:workspace / site:create). - Account sign-in: POST /api/magic-link finds an existing user by email (no account enumeration — identical response either way), mints an account-scoped token, and emails ${APP_URL}/account?token=…. src/lib/account/session.ts verifyAccountToken() is the gate: it returns a userId only for a valid account-scoped token. Per-site tokens are rejected there (unit-tested in session.test.ts). Verified - Per-site workspace links (alerts, CDI) are minted elsewhere and are unaffected by the account flow.

2. API keys (programmatic). src/lib/api/keys.ts — gs_live_ + 40 base62 chars; only the SHA-256 hash is stored (ApiKey.hashedKey); the plaintext is shown once at creation. Scopes: checks:write, sites:read, sites:write, usage:read, webhooks:manage. src/lib/api/auth.ts authenticate(request, requiredScope?) resolves the key by hash, checks revokedAt and scope, and best-effort stamps lastUsedAt. Verified

Authorization. Tenant isolation is enforced in the repository/store layer, not the UI: every site/observation/check/key/webhook read is scoped by userId (the SiteCheck is scoped by email match to the key owner, since it has no userId — Verified, documented limitation in §G).

Route classes. Public: SEO pages, GET /api/v1 + /openapi.json. Account-token: /account, /api/account/**. API-key: /api/v1/** (except the public index). Admin-secret: /admin, POST /api/analyze, POST /api/cron/deliver-webhooks (ADMIN_SECRET via x-admin-secret).

H. Webhooks & asynchronous processing

Two provider webhooks/async systems. Keep them separate.

1. Inbound — Stripe webhook (POST /api/stripe/webhook). Verifies the Stripe signature (STRIPE_WEBHOOK_SECRET), and provisions only on checkout.session.completed — never before confirmed payment. It also fires the server-side GA4 purchase (Decision D, §L). Idempotency uses in-schema signals: SiteCheck.paid (first-payment flag) and the subscription "created" flag from a prior findUnique — so a duplicate Stripe delivery doesn't double-provision or double-count the purchase. [Verified by inspection; Runtime-verify against a real Stripe test event.]

2. Outbound — Ground Stasis webhooks (customer-facing). New this cycle. - Model: WebhookEndpoint (url + AES-GCM-encrypted secretCipher + subscribed events[]) and a durable WebhookDelivery outbox. - Emission: src/lib/api/webhooks/emit.ts — when a monitoring run inserts a new alert (persistAnalysis captures the inserted alerts via its create-closure, so duplicates never re-emit), it maps alertType → event (events.ts) and enqueues a delivery per subscribed active endpoint. Guarded with try/catch in src/lib/jobs/run.ts so a webhook failure cannot break a monitoring run. - Delivery worker: src/lib/jobs/deliver-webhooks.ts runWebhookDeliveries() — claims due rows, SSRF layer 2 (resolves the hostname and re-checks every resolved IP against the private/reserved blocklist in ssrf.ts before connecting), decrypts the secret, signs (sign.ts, Stripe-style t=…,v1=… HMAC header X-GroundStasis-Signature), POSTs with an 8s timeout, then records the outcome. Retries use exponential backoff (delivery-policy.ts, 30s→6h, max 6 attempts). Delivery is at-least-once — consumers dedupe on the X-GroundStasis-Delivery id. - Trigger: netlify/functions/scheduled-webhook-delivery.ts (every minute) → admin-gated POST /api/cron/deliver-webhooks. - Security: src/lib/api/webhooks/ssrf.ts layer 1 (reject non-https, credentials-in-URL, non-443 ports, localhost/internal names, private/reserved IP literals) + layer 2 (resolve-time IP recheck). [Verified; unit tests for sign/ssrf/secret-crypto/delivery-policy/events all pass in the isolated harness.]

Verified server-side purchase (Decision D). src/lib/analytics-mp.ts sends a GA4 Measurement Protocol purchase from the Stripe webhook after confirmed payment (GA4_API_SECRET, transaction_id = Stripe session id, value/currency from the session). The visitor's GA4 client_id is captured at checkout (getGaClientId() — gtag, falling back to the _ga cookie) and carried through Stripe metadata. If no client_id, the purchase is skipped, never faked. Idempotent via the in-schema first-payment/created flags. [Verified by inspection; Runtime-verify in GA4 DebugView.]

Runtime-verify A tracking call in code does not prove the event arrives in GA4. Confirm in GA4 Realtime/DebugView, and confirm which events are marked key events/conversions (that's configured in the GA4 UI, not the repo).

M. Deployment, configuration & environments

Deploy (correct path): Git-connected Netlify CI. Push to GitHub → Netlify builds on its Linux CI (npm run build → prisma generate && next build, with @netlify/plugin-nextjs v5) → deploy. Env vars live in the Netlify dashboard; the build uses those (not any local .env).

Important Do not deploy this app with netlify deploy from the Windows CLI. It was observed to build successfully but publish Next v5 routing incorrectly, 404-ing every route. Drag-and-drop is static-only and also won't work (no serverless functions). Use Git-connected CI, or roll back in the Netlify dashboard (Deploys → a known-good deploy → Publish deploy) to restore instantly.

The console email provider prints magic links to the npm run dev terminal.

N. Security, privacy & data integrity

Confirmed-good: API-key hashing (store only SHA-256); magic-link signing + expiry + rotation; account/site tenant isolation in the repository layer; Stripe webhook signature verification; webhook SSRF guard (two layers) + encrypted signing secrets at rest; GeoJSON validation; no secrets client-side; private site data served noindex and kept out of URLs; the DATA-GAP integrity rule.

Risks to track: - Risk Shared dev/prod database. Use the Neon dev branch for local work; never run migrations or write-path tests against prod .env. (A local build that reads a dev .env must not be deployed — use CI.) - Risk No app-level rate limiting on /api/magic-link. The public API is rate-limited (ledger), but the sign-in endpoint relies on the no-enumeration response; add edge/middleware rate limiting in production. - Runtime-verify Stripe idempotency & GA4 purchase under real duplicate deliveries. - Note Webhook delivery is at-least-once by design — consumers must dedupe on delivery id. - Watch Geo/doorway pages — keep them substantive.

Rank before acting: shared DB (highest), then magic-link rate limiting, then the runtime verifications.

O. Troubleshooting runbooks

Each: symptom → likely cause → where to look → safe fix → verify.

  1. Whole site 404s after a deploy. → Deployed via the Windows Netlify CLI (v5 routing not published). → Netlify Deploys list. → Roll back to a known-good deploy (Publish deploy), then deploy via Git-connected CI. → / and /api/v1 return content.
  2. Satellite provider auth/API failure. → CDSE creds/quota. → sentinelhub-provider.ts logs; capabilities() in env.ts. → Falls back to demo if unconfigured; fix creds. A failure must show as DATA GAP, never stasis. → Run scripts/validate-cdse.mjs.
  3. No usable observations / unexpected DATA GAP. → Clouds or maxDaysSinceUsableObservation exceeded. → analysis/config.ts thresholds + the observation's qualityStatus. → Expected behavior, not a bug; wait for a clear pass.
  4. Magic-link sign-in shows nothing locally. → APP_URL not localhost, or the email isn't a User row, or MAGIC_LINK_SECRET unset. → §F, §M. → Set APP_URL=http://localhost:3000, add a user via npx prisma studio, set a local secret; link prints in the dev terminal.
  5. Stripe payment didn't provision. → Webhook not received/verified. → /api/stripe/webhook; Stripe dashboard → webhook deliveries. → Confirm STRIPE_WEBHOOK_SECRET; provisioning only fires on checkout.session.completed. → Check the Subscription/SiteCheck row.
  6. Webhook not delivered. → WEBHOOK_ENC_KEY unset, endpoint inactive/invalid URL, or SSRF-blocked. → WebhookDelivery.status/attempts; Netlify function logs for scheduled-webhook-delivery. → Fix endpoint; retries resume automatically.
  7. Monitoring job didn't run. → Scheduled function error / APP_URL/ADMIN_SECRET. → Netlify function logs. → Re-trigger POST /api/analyze manually with the admin secret.
  8. Missing/duplicate GA4 events. → Consent, ad-blockers, or the event not marked a key event. → GA4 DebugView. → Verify in the GA4 UI (runtime only).

Never run destructive DB commands or apply migrations against production without a backup, an environment check, and an explicit decision.

P. Junior developer onboarding

  1. Read README.md, ARCHITECTURE.md, ALGORITHM.md, SATELLITE_DATA.md, then this handbook §A–§E.
  2. npm install.
  3. Create a local .env from .env.example: point DATABASE_URL at the Neon dev branch, set APP_URL=http://localhost:3000, a local MAGIC_LINK_SECRET, WEBHOOK_ENC_KEY. Leave SATELLITE_PROVIDER unset (demo) to start.
  4. npx prisma generate, then npm run dev. The app runs in demo mode with an empty-ish env.
  5. Trace a check: open /construction-activity-check, follow CheckFlow → /api/checkout.
  6. Trace fulfillment: read /api/stripe/webhook with Stripe test mode + a test price.
  7. Trace auth: POST /api/magic-link with a user's email → grab the link from the terminal → /account.
  8. Trace monitoring: read runScheduledAnalysis in src/lib/jobs/run.ts.
  9. Make a small change (e.g., a tool's copy), run npm run lint + npm test + npm run build.
  10. Commit, push — Netlify CI deploys. Verify on the deploy's URL.

Tests: npm test (vitest). The analysis engine, api libs, and webhook libs have unit tests.

Q. FAQ

  • Where does satellite data come from? CDSE Sentinel-2 L2A via the Statistical API (§C).
  • What does a status mean? A 0–100 stasis score bucketed ACTIVE/WATCH/REVIEW/STASIS, with protective overrides; low confidence caps STASIS to REVIEW (§C, ALGORITHM.md).
  • Why might there be no recent observations? Clouds/revisit — reported as DATA GAP, never inactivity.
  • Where's the analysis logic? src/lib/analysis/ (pure).
  • Where are users/sites stored? Postgres via Prisma; access through src/lib/db/repository.ts.
  • How does auth work? Magic-link tokens for humans, API keys for programs (§F).
  • How does a $9 check become a report? /api/checkout → Stripe → webhook marks paid → analyzeSite → result on SiteCheck → emailed /check/[token].
  • How does a subscription activate? Webhook recordStripeSubscription grants seats (fail-safe to 1).
  • What if Stripe sends a webhook twice? In-schema first-payment/created flags make provisioning + the GA4 purchase idempotent (§H, §L) — Runtime-verify.
  • How are monitoring checks triggered? scheduled-analysis every 6h → /api/analyze.
  • How do I add a GA4 event? Add to GA_EVENTS and call track() (§L).
  • How do I add an SEO page/tool? New src/app/<slug>/page.tsx (+ a components/tools/*), add to sitemap.ts, cross-link.
  • How do I change pricing safely? Edit src/lib/billing/pricing.ts + set the matching Stripe price id env vars; never hardcode price_….
  • Which operations are unsafe in production? Migrations against prod .env, deploying a locally built .env, the Windows Netlify CLI deploy, rotating WEBHOOK_ENC_KEY.
